# Topologies, Kong versions and Enterprise

## What the tests cover

Kong runs custom plugins the same way in every topology. What differs is **where the configuration comes from** and **what the plugin can reach**. Every integration test in this repo runs once per strategy (`helpers.all_strategies()`):

| Topology | How it's tested | What to watch for in your plugin |
|---|---|---|
| **Traditional** (Kong + Postgres) | `[#postgres]` tests | Nothing special. `kong.db` is available. |
| **DB-less** (declarative `kong.yml`, decK) | `[#off]` tests | No database: `kong.db` entities are read-only and come from the declarative config. Custom DAOs and migrations don't apply. |
| **Hybrid: data plane** | `[#off]` tests | A DP runs DB-less with the config pushed by the CP. Same rules as DB-less; for example, a DP can't look up entities that aren't in the pushed config. |
| **Hybrid: control plane** | `01-schema` tests | The CP only stores and validates plugin configuration. It needs `schema.lua` (and the plugin installed), but never runs `handler.lua`. |
| **Konnect** | `01-schema` tests | You upload only `schema.lua` to the control plane, and it must not `require()` anything. The schema tests check this. No `api.lua`, custom DAOs or migrations. Kong 3.15+ can also stream the plugin from the CP to the DPs. |

**Deploying** a custom plugin, in short:
- Put `handler.lua` + `schema.lua` on **every** Kong node (CP and DPs). Do it with luarocks, or by copying them into `/usr/local/share/lua/5.1/kong/plugins/<name>/` in a custom image.
- Enable it with `KONG_PLUGINS=bundled,<name>`, or `plugins = bundled,<name>` in kong.conf.

In hybrid mode, update the CP before the DPs when the schema changes. Otherwise DPs reject the new config with `required field missing` errors.

## A real hybrid (CP/DP) integration test

The examples don't include one, but Kong's test helpers support it. You start two Kong instances in one spec, using the clustering certificates that come with the test helpers. This snippet was checked against Kong 3.9.2 with a plugin generated by `scripts/new-plugin.sh`; adapt the route and the assertion to your plugin.

```lua
lazy_setup(function()
  helpers.clean_prefix()
  local bp = helpers.get_db_utils("postgres", nil, { PLUGIN_NAME })
  local route = bp.routes:insert({ hosts = { "hybrid.test" } })
  bp.plugins:insert({ name = PLUGIN_NAME, route = { id = route.id } })

  assert(helpers.start_kong({            -- control plane, with the database
    role = "control_plane",
    database = "postgres",
    cluster_cert = "spec/fixtures/kong_clustering.crt",
    cluster_cert_key = "spec/fixtures/kong_clustering.key",
    cluster_listen = "127.0.0.1:9005",
    nginx_conf = "spec/fixtures/custom_nginx.template",   -- also runs the mock upstream (DPs don't)
    plugins = "bundled," .. PLUGIN_NAME,
  }))

  assert(helpers.start_kong({            -- data plane, DB-less, gets its config from the CP
    role = "data_plane",
    database = "off",
    prefix = "servroot2",
    cluster_cert = "spec/fixtures/kong_clustering.crt",
    cluster_cert_key = "spec/fixtures/kong_clustering.key",
    cluster_control_plane = "127.0.0.1:9005",
    proxy_listen = "0.0.0.0:9002",
    nginx_conf = "spec/fixtures/custom_nginx.template",
    plugins = "bundled," .. PLUGIN_NAME,
  }))
end)

lazy_teardown(function()
  helpers.stop_kong("servroot2")
  helpers.stop_kong()
end)

it("works on the data plane", function()
  -- the DP receives its config asynchronously: retry until it's there
  assert.eventually(function()
    local client = helpers.http_client("127.0.0.1", 9002)
    local r = client:get("/request", { headers = { host = "hybrid.test" } })
    client:close()
    return r.status == 200 and r.headers["X-Example-Response"] ~= nil
  end).with_timeout(15).is_truthy()
end)
```

## Kong versions

Pongo picks the Kong version from `KONG_VERSION`:

| `KONG_VERSION` | Kong |
|---|---|
| *(unset)* | **3.9.2**, the latest open-source (CE) release; this repo's default |
| `3.9.x` | latest 3.9 CE patch release |
| `3.10.0.14` | that exact Enterprise version (four parts = Enterprise, image `kong/kong-gateway`) |
| `3.10.x.x` | latest 3.10 Enterprise patch release |
| `stable-ee` | latest Enterprise release |

- `pongo status versions` lists every available version.
- Each version gets its own test image (several GB), built on first use. `pongo clean` removes them.
- Kong stopped publishing open-source images after 3.9. Anything newer is Kong **Enterprise**.

### Enterprise and licenses

- **Kong Enterprise starts without a license.** The complete test suite of this repo (both examples, Postgres and DB-less) passes on `KONG_VERSION=3.10.0.14` without a license. This was checked on 2026-10-09 with Pongo 2.29.0.
- **When you need a license:** your plugin uses Enterprise-only features, or your tests enable Enterprise plugins (e.g. `openid-connect`, `mtls-auth`) or Enterprise entities. Get the license JSON from your Kong account or your customer.

Never commit the license: `*license*.json` and `*.lic` are git-ignored. Pass it in through the environment:

```bash
KONG_VERSION=3.10.0.14 KONG_LICENSE_DATA="$(cat ~/kong-license.json)" pongo run
```

Enterprise-only features your plugin may use (Dev Portal entities, `kong.enterprise_edition.*`, Enterprise plugins' modules such as `kong.plugins.mtls-auth.*`, …) are only available when you test on an Enterprise version.

### Testing against your company's Kong image

If your gateways run a custom image (with other plugins, patches or certificates), use it as the base for the test image:

```bash
KONG_IMAGE=registry.example.com/kong/kong-gateway:3.10.0.14-ubuntu pongo run
```

- Pongo reads the Kong version from the image.
- The version must be one Pongo knows; see `pongo status versions`.
